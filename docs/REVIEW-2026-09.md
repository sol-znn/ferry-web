# Code review, September 2026

A full read of `wasm/`, `ui/` and `scripts/`, looking for defects rather than
style. Everything below was found, confirmed against the actual behaviour, and
fixed in the same pass; each entry names the fix and, where one exists, the test
that now holds it.

Two findings are the reason this document exists. **Z1** and **Z2** compose into
a working theft of the Bitcoin leg: together they let a counterparty publish a
Zenon HTLC holding a token they issued themselves, in an amount worth nothing,
and have Ferry report *"verified: hashlock, parties, amount and expiry all
match"* on the one screen a user consults before funding.

Severities are about money, not about tidiness:

- **Critical** — a counterparty can take funds, or a user is told something
  false about safety.
- **High** — funds can become unrecoverable, or a check silently does not run.
- **Medium** — wrong state, wrong advice, or a path that fails when it should
  not.
- **Low** — robustness and correctness with no path to loss.

---

## Critical

### Z1 — The Zenon HTLC's token standard was never verified

`wasm/znn/client.go`, `wasm/manager.go`

`VerifyParams` had no field for the agreed token, `Verify` never looked at
`info.TokenStandard`, and `VerifyZenon` then *overwrote* the swap's agreed
`TokenStandard` with whatever the entry held — so a second verification of the
same HTLC could not have caught it either.

Every other check passes for free in the attack. The hashlock is the agreed one;
the parties are the agreed ones; the expiry is correctly ordered. The only thing
wrong is that the ten units locked are ten units of a token issued that morning.

**Fixed.** `VerifyParams.ExpectTokenStandard` is set from the swap's own agreed
token and compared in `Verify`. `VerifyZenon` no longer overwrites the agreed
value; the observed one is recorded separately in `ZenonLeg.ObservedToken` and
shown on the card beside it when the two differ. Because "which token" is now
load-bearing, a blank token field resolves to ZNN through `ZenonLeg.AgreedToken`
— the creation form has always said blank means ZNN, and a swap record written
before the field was defaulted still has to verify.

*Tests:* `TestZenonVerifyRefusesTheWrongToken`, `TestAgreedTokenDefaultsToZnn`.

### Z2 — The amount check collapsed to nothing for an unknown token

`wasm/manager.go`, `wasm/znn/client.go`

go-zenon answers `embedded.token.getByZts` for an unknown ZTS with `(nil, nil)`
— which reaches the client as `{"result": null}`. `json.Unmarshal("null", &Token{})`
succeeds and leaves `Decimals` at `0`. `decimalToBaseUnits("10", 0)` is then
**10 base units**, not 10·10⁸, so an HTLC holding a ten-millionth of the agreed
amount cleared the check.

Reached directly by Z1: the decimals were looked up for the token the *entry*
named, which in the attack is the attacker's own.

**Fixed** in three places, because one would have been enough only until the
next caller. `Client.call` refuses a null or absent result rather than decoding
it into a zero struct. `GetToken` requires the node to echo back the ZTS that
was asked for and refuses an implausible `decimals`. `VerifyZenon` looks up the
**agreed** token, never the observed one.

## High

### Z3 — A skipped amount check was reported as a passed one

`wasm/manager.go`

If `GetToken` failed, or the agreed figure would not parse, `MinAmount` was left
nil, `Verify` returned nil, and the card printed *"verified: hashlock, parties,
amount and expiry all match"*. A check that did not run is indistinguishable from
one that passed — which is exactly the reasoning `auditLegOrdering` already
applied on the Bitcoin side, where a skipped ordering check logs a NOTE saying so.

**Fixed.** Every failure path now sets `VerifyParams.AmountUncheckable`, and
`Verify` turns that into a refusal naming what could not be checked and why.

*Test:* `TestZenonVerifyRefusesAnUncheckableAmount`.

### S1 — A swap could be created with no destination address, funded, and then not spent

`wasm/manager.go`, `ui/src/pages/ActivePage.vue`, `ui/src/components/SwapCard.vue`

`destAddr` was optional. Both branches of the contract pay it and there is no
other, so without one:

- `Refresh` skipped pre-signing the refund — silently, with no log line, while
  the card kept showing "Save the recovery file" for a file that had no
  transaction in it;
- `Redeem` and `Refund` from the card passed `swap.destAddr ?? ''` and failed
  with "a destination address is required";
- nothing in the UI could supply one.

The user discovered it after the money was already in the contract, and the only
way out was the Recover page with a hand-typed address.

**Fixed.** `Create` requires a destination and validates it against the swap's
network. The form marks it required and says why. For records restored from an
older backup, the card grows a destination field when one is missing, and the
address given there is adopted onto the swap. `Refresh` says once, in the event
log, when it could not pre-sign and why.

*Tests:* `TestCreateRequiresADestination`,
`TestRefreshSaysWhyTheRefundWasNotPreSigned`, plus a smoke check.

### P1 — `ParseContract` accepted locktimes `OP_CHECKLOCKTIMEVERIFY` will not read

`wasm/htlc.go`

`scriptNum` allowed operands up to 8 bytes in any encoding. Bitcoin reads a CLTV
operand as a CScriptNum of at most **5** bytes, minimally encoded. So a contract
whose locktime was padded to 8 bytes, or padded non-minimally within 5, parsed
here into a perfectly sensible timestamp, passed the audit, passed the leg
ordering — and had a refund branch that no node will ever execute.

The loss falls on the funder, and the audit is performed by the redeemer, so no
other check in the system was positioned to catch it. The parser is the last
point before funding at which it can be caught at all.

**Fixed.** `scriptNum` takes the width the engine allows at that position — 4
for the `OP_SIZE` operand, 5 for CLTV — and enforces `MINIMALDATA`'s
minimal-encoding rule, which is what the local script engine would have applied
at signing time, an hour too late.

*Test:* `TestParseRejectsLocktimesTheScriptEngineWillNot`.

## Medium

### M1 — `absorbSpend` trusted the backend's txid without checking it spent our output

`wasm/manager.go`

`OutspendOf` named a transaction, `RawTx` fetched it, and whatever came back
decided between `redeemed` and `refunded`. Nothing checked that the transaction
actually spends `funding.TxID:Vout`. A wrong answer files a live swap away as
settled, which takes it off the active list and stops `Refresh` looking for the
real spend.

**Fixed.** The fetched transaction must contain an input spending the recorded
outpoint; otherwise the answer is refused and the event log says so.

*Tests:* `TestRefreshIgnoresASpendThatIsNotOurs` — using the strongest form of
the wrong answer, a transaction carrying a *valid* preimage for this swap's hash,
so only the outpoint check can catch it — and
`TestRefreshLearnsTheSecretFromOurOwnOutpoint` for the case that must still work.

### M2 — Verification wrote its findings onto the swap even when it failed

`wasm/manager.go`

`HtlcID`, `ExpirationTime`, `TokenStandard`, `Amount` were all assigned before
`Verify` ran. Three consequences: `auditLegOrdering` later compared against an
expiry taken from a *rejected* HTLC; `planZenonLeg` saw a non-empty `HtlcID` and
stopped producing the advice needed to build a correct replacement; and the
agreed token was replaced by the observed one (see Z1).

**Fixed.** The agreed terms are never overwritten. Observed values are still
recorded — the card needs them to explain a rejection — but `auditLegOrdering`
only trusts `ExpirationTime` when `Verified` is set, and `planZenonLeg` keeps
advising while the HTLC is unverified.

*Test:* `TestAuditLegOrdering/an_unverified_zenon_expiry_is_not_trusted`.

### M3 — `Rebuild` reported "valid from" using the file's `lockTime`, not the contract's

`wasm/recover.go`

The transaction was built from `details.LockTime`, parsed out of the contract,
but `ValidFrom` and `NotYet` came from `rf.LockTime` — an editable field the file
also carries. The page already refuses a file whose `contractAddr` does not hash
to its own `contractHex`; the locktime had no such check. A stale or edited value
told the user to wait the wrong length of time, on the screen they reach when
everything else has already failed.

**Fixed.** `ValidFrom` comes from the contract, and a `lockTime` field that
disagrees with it makes the file inconsistent and refused, in the same words as
the address check.

*Tests:* two smoke checks.

### M4 — `Import` accepted arbitrary records, and one bad record aborted the whole import

`wasm/store.go`, `wasm/api.go`, `ui/src/components/BackupPanel.vue`

Nothing validated an imported swap. `Key` could be nil, the network unknown, the
contract unparseable. `handleOffer` and `handleRecovery` then dereference `Key`
without asking — a panic inside the module, which the bridge's `recover` catches
but which is a poor answer to a file the user chose. Separately, a record whose
id was not storable made `Save` fail, which returned from `Import` mid-run and
reported a partial import as an error.

**Fixed.** `Swap.validate` checks the id, the network, the three halves of the
key *against each other*, the secret against its own hash, and the contract
against the template. Bad records are counted and reported rather than aborting
the run, and the panel now says plainly that records were refused — a swap that
did not come back is a contract this browser can no longer spend.

*Tests:* `TestImportRejectsRecordsThatCouldNotHaveComeFromHere`, plus two smoke
checks.

### M5 — `await` could hang forever without `AbortController`

`wasm/httpx/httpx_js.go`

The timeout was enforced *only* by `AbortController`: aborting is what makes the
promise settle. Where it is absent, `await` blocked on its channel with no
`ctx.Done()` case, so the exact failure the timeout exists for — a host that
accepts the connection and then says nothing — parked the goroutine for the life
of the page.

**Fixed.** `await` takes the context and selects on it. The `js.Func` callbacks
are now released when the *promise* settles rather than when `await` returns:
releasing them on the ctx path would free callbacks JS still holds, which the
runtime answers with "call to released function" when they eventually fire.

### M6 — Txids from the backend went into URLs unvalidated

`wasm/chain/esplora.go`

`RawTx` and `OutspendOf` interpolate a txid into a request path, and every txid
they receive came from a *previous response* — a value the node chose. A value
carrying `/` or `..` walks the path of the request built from it, and a value
that is not a txid at all had no business being written onto a swap record as
its funding outpoint either.

**Fixed.** `ValidTxID` gates both calls, the txids in an `AddressUTXOs` response
and the spender in an `OutspendOf` response. The address path segment is escaped.

### M7 — Chain actions stayed enabled when the swap's network and the app's disagreed

`ui/src/components/SwapCard.vue`

`networkMismatch` rendered a warning; Refresh, Redeem, Refund and Verify stayed
clickable, so a mainnet swap could be pointed at a testnet Esplora. A warning
beside a live button is one people click past.

**Fixed.** Every chain-touching action is disabled on a mismatch. Auditing and
the offer string are not — both are pure, and work with every node in the world
unreachable, which is precisely when they are worth having.

## Looked at and left alone

Not everything that could be tightened should be:

- **`connect-src *` in the CSP.** Already argued through in `SECURITY.md` and
  the argument holds: an allowlist would mean this page choosing your node for
  you, and code that can execute on this origin can read `localStorage`
  directly. `script-src` is the directive doing the work.
- **Records are unencrypted at rest.** The README's first known gap, and a
  design change rather than a defect. Nothing here alters it.
- **`pickFunding` ignores confirmation status.** Deliberate: seeing unconfirmed
  funding immediately is what lets the refund be pre-signed on sight, and the
  event log records `confirmed=` either way.
- **`scripts/regtest-esplora.mjs` converts BTC to satoshis through a float.**
  It is a development shim for regtest, says so at the top, and the values it
  handles are far inside double precision.
- **No subresource integrity on `ferry.wasm`.** It is same-origin, and the real
  answer is the reproducible build already listed as an open item in
  `SECURITY.md`.
